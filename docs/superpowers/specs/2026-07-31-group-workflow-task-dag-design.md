# 群协作工作流任务 DAG 设计

## 目标

将群协作从按聊天消息、时间心跳与群主催办推进，改为以可验收任务组成的有向无环图（DAG）推进。Agent 仅执行分配给自己的就绪任务；群主只处理阻塞、验收异常和工作流变更确认。成员消息仍默认对管理员可见，但不再作为状态推进的依据。

第一版覆盖全部生命周期阶段。阶段保留为不可跳过的里程碑，任务为实际调度单元。

## 已确认的规则

- 阶段按既有位置顺序推进，后续阶段不能提前完成或被跳过。
- 同一阶段中，满足全部前置依赖的任务可以并行。
- 任务只在全部前置任务验收通过后成为 `ready`。
- 任务完成必须提交结构化证据，并通过任务验收契约；文档、纪要或群主口头说明不能替代代码、测试或其他要求的实际交付物。
- 阻塞、失败、验收不通过会阻断依赖链的下游任务，不自动跳过。
- 群主可新增或拆分尚未开始的任务。
- 重连依赖或修改验收契约，必须形成变更申请并由群主确认。已开始任务不得被静默篡改。
- 群主在成员列表中保持置顶；管理员主要与群主沟通。

## 数据模型

保留 `GroupWorkflow`、`GroupWorkflowStage`、`GroupWorkflowItem` 及审计事件模型。`GroupWorkflowItem` 是任务实体，增加：

- `acceptance_criteria`：任务级验收契约 JSON；不从阶段验收标准推断完成。
- `started_at`、`completed_at`、`failed_at`：任务生命周期时间。
- `failure_code`、`failure_summary`：模型或执行失败的可读摘要。
- `revision`：任务变更版本，与现有乐观锁版本配合。

新增 `group_workflow_task_dependencies`：

- `id`、`workflow_id`、`predecessor_item_id`、`successor_item_id`、`created_at`。
- 唯一约束：`(predecessor_item_id, successor_item_id)`。
- 外键指向任务，工作流删除时级联删除。
- 检查约束禁止任务依赖自身；应用层拒绝跨工作流依赖、缺失依赖、重复边、有环和指向后续阶段的依赖。

任务状态扩展为：

`pending`、`ready`、`in_progress`、`awaiting_approval`、`done`、`blocked`、`failed`。

第一版不提供跳过或删除任务的完成路径。第一版的依赖策略为“全部前置任务完成”（all-of）；不加入任一依赖完成即可继续的模式，避免在关键交付中产生歧义。

## 草案与创建

AI 工作流草案的结构扩展为：每个任务包含稳定 `item_key`、负责人、`depends_on`、任务级 `acceptance_criteria` 与证据要求。规划模型可将阶段内工作并行化，也可声明来自先前阶段任务的依赖；不得引用后续阶段任务。

草案确认时，服务在一个事务中：

1. 校验成员引用、任务键唯一性和验收契约。
2. 按阶段及任务键解析依赖。
3. 校验所有 DAG 规则并生成任务、依赖边和初始审计事件。
4. 将首个阶段中没有前置依赖的任务设为 `ready`，其余任务为 `pending`。
5. 在事务提交后，为每个 `ready` 任务创建带幂等键的派发事件。

无效草案返回可读错误；不创建部分工作流或部分依赖。

## 运行时调度

调度的唯一状态驱动为任务事件：任务开始、证据提交、验收通过或失败、显式重试、变更确认。事件处理在同一数据库事务中锁定受影响任务并重新计算其后继任务，使用事件幂等键和版本号避免重复派发。

- 负责人只收到其 `ready` 任务：目标、前置产物、验收标准、证据入口和失败/阻塞上下文。
- Agent 只能在自己被分配且已就绪的任务上启动、提交证据或报告阻塞；不能以群聊内容标记其他任务完成。
- 证据校验失败时，任务回到 `in_progress` 或 `blocked`，并保留失败说明；后继任务维持 `pending`。
- 模型调用或执行失败时，当前任务记录为 `failed`，所有下游任务显示依赖阻塞。系统不盲目自动续跑；群主可发起显式重试。
- 任务从 `failed` 或 `blocked` 重试成功后，调度器重新计算下游，不重复已派发的其他任务。

阶段状态由任务状态派生：只有当前阶段的全部任务均为 `done`、没有未决变更且阶段验收条件满足时，阶段才可完成并解锁下一阶段的根任务。阶段负责人、群主或聊天消息都不能绕过这一规则。

## 群主变更确认

变更通过独立的申请/确认流程执行，记录申请者、修改前后内容、受影响任务、阻塞影响、确认人和时间：

- 新增和拆分未开始任务：群主可直接确认并写入；新增任务仍必须通过 DAG 校验。
- 重连依赖、修改验收契约：先生成影响预览，再由群主确认后写入；第一版不支持删除任务，以免绕过已承诺的交付。
- 涉及已开始、已完成或正在验收任务的变更：拒绝直接修改，要求新建后续任务或群主发起受控返工。
- 每一次变更写入工作流事件，供任务详情、群消息与 AI 监控关联展示。

## 接口与前端

新增或扩展工作流接口：

- 工作流图：返回阶段、任务、依赖边、每项状态、负责人、证据摘要和阻塞原因。
- 任务详情：返回验收契约、前置/后继、执行与 AI 调用上下文、证据和审计事件。
- 任务操作：开始、提交证据、报告阻塞、显式重试。
- 变更：创建申请、获取影响预览、群主确认或拒绝。

`GroupWorkflowTab` 改为工作流管理面板：

- DAG 视图：显示节点状态与依赖边，支持筛选阶段与负责人。
- 阶段视图：显示不可跳过的里程碑及其完成条件。
- 就绪队列：显示已派发和待派发任务。
- 阻塞链：从当前阻塞任务向上展示失败或未验收的前置任务。
- 任务侧栏：展示任务详情、产物、验收记录、执行消息和关联的 AI 监控数据。
- 群主待处理区：只显示变更确认、阻塞/失败与验收异常；不显示泛化催办。

群聊继续默认展示成员执行消息，但所有系统执行消息均附带任务标识并链接到任务详情。聊天不再改变任务状态。

## 错误处理与审计

- 草案或群主变更出现环、缺失依赖、非法阶段方向、越权负责人时返回明确的 4xx 业务错误。
- 并发状态更新发生版本冲突时返回可重试冲突，不重复派发任务。
- Agent、工具或模型错误记录任务失败代码、摘要、时间和可访问的 AI 监控关联；对管理员显示经过整理的上下文，不暴露系统内部指令。
- 所有状态变更、证据提交、重试和变更确认写入 `GroupWorkflowEvent`，以幂等键防止重复记录。

## 测试与验收

后端测试覆盖：

1. 依赖引用、重复边、自依赖、循环、后续阶段依赖的拒绝。
2. 根任务派发、同阶段并行、依赖完成后释放下游。
3. 失败、阻塞、验收失败对下游和阶段推进的影响。
4. 阶段不可跳过与任务证据不足时不得完成。
5. Agent 只能操作自己就绪的任务。
6. 群主确认变更的权限、影响预览、审计和已开始任务保护。
7. 重复事件、并发更新与任务派发幂等性。

前端测试覆盖 DAG 状态显示、阻塞链、群主确认入口、任务详情与空/错误状态。

验收成功的标志是：创建一个覆盖所有生命周期阶段的工作流后，只有根任务被派发；依赖完成并验收后才释放后继；任意失败或缺少代码/测试等所需证据时，工作流不能进入下一阶段；群主确认的变更完整反映在图、任务历史和群消息中。
